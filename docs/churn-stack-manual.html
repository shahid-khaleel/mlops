00Orientation

Overview & purpose

This document exists to answer one question precisely: what is actually running, why, and how do the pieces talk to each other? It covers a single scenario end to end — a churn-prediction RandomForest, trained locally, tracked and versioned in MLflow, served by KServe, and orchestrated by a lean slice of Kubeflow — all on one Minikube node.

Business problem
Predict customer churn
Training data
customers.csv
age, tenure, monthly_charges, support_calls, contract_type
Model
RandomForest
scikit-learn Pipeline, one-hot + classifier
Registry versions
v1 – v6
churn-model in MLflow

Four tools sit on top of Kubernetes, each answering a different question about the same model:

  • MLflow — what did we train, with which parameters, and how well did it score?
  • KServe — given a trained model file, how do we turn it into a prediction endpoint without writing serving code?
  • Kubeflow Trainer — if training itself needed to run distributed, inside the cluster, what would coordinate that?
  • Kubeflow Dashboard (Istio + Dex + Profiles) — how does a human log in and see any of this in a browser, safely?

Two things were deliberately not built, by explicit decision: Kubeflow Pipelines (workflow orchestration) and any CI/CD. Both are noted where relevant so their absence reads as a choice, not a gap.

01Topology

System architecture

One Minikube node, twelve namespaces, two long-running host processes outside the cluster. Namespaces are drawn as lanes; every pod named below is a real pod running at the time this manual was written.

02Division of labor

Why each layer exists

Every tool here answers a question the layer below it cannot. None of them overlap in responsibility, which is the actual test of whether a piece belongs in the stack.

LayerAnswersDoes not know about
KubernetesHow to keep a container running, reachable, and rescheduled on failure.Models, experiments, training runs — it runs arbitrary containers, nothing ML-specific.
MLflowWhat was trained, with which parameters, which metrics resulted, and which artifact came out.How that artifact gets served — MLflow only tracks and stores, it never runs a serving endpoint here.
KServeGiven a model file and its framework, how to run a matching pre-built server and expose /predict.Where the model came from, or how it was trained.
Kubeflow TrainerHow to turn a TrainJob object into the actual pod(s) that run a training script, including coordinating multiple nodes.Tracking metrics or serving results — installed but intentionally unused for this small model.
Kubeflow Dashboard + Istio + DexHow a human authenticates once and reaches a namespace-scoped view of what they own.Anything about model quality or serving mechanics — pure auth/UI plumbing.

Deliberately excluded: Kubeflow Pipelines, Katib, Notebooks, CI/CD, Argo, Terraform. Each would answer a real question this stack doesn't currently ask.

03Vocabulary

Glossary

Every term used elsewhere in this manual, defined against this exact deployment — not the general case.

Experiment / Run
A run is one execution of train.py; an experiment (churn-prediction) groups related runs for comparison.
Why it matters: six runs exist (v1–v6 below), each with different n_estimators/max_depth, all comparable side by side in the MLflow UI.
Backend store
Where MLflow keeps searchable metadata — params, metrics, run status. Here: SQLite at mlflow.db.
Why SQLite: the Model Registry requires a database backend; a plain-file store can't support it.
Artifact store
Where the actual model files live. Here: the local ./mlruns folder.
Note: MLflow 3.x saves sklearn models as model.skops, not the older .joblib — see §10.
Model Registry
Gives a trained artifact a stable name (churn-model) and an incrementing version, independent of which run produced it.
Why: serving code can reference models:/churn-model/6 without knowing which run trained it.
InferenceService
A KServe custom resource: "here is a model and where to find it — please serve it." Six lines of YAML replace a hand-written Deployment + Service.
Instances here: churn-model, sklearn-iris — each deployed twice, into default and kubeflow-user-example-com.
Predictor
The part of an InferenceService that actually loads the model and answers requests — the generated Deployment KServe manages for you.
Standard mode: a plain Kubernetes Deployment, no Knative involved.
ClusterServingRuntime
A reusable blueprint mapping a model framework (e.g. sklearn) to the container image that can serve it.
Used here: kserve-sklearnserver — the built-in scikit-learn server.
Standard (RawDeployment) mode
KServe's install mode that skips Knative + Istio entirely, generating plain Deployments/Services instead.
Trade-off accepted: no scale-to-zero autoscaling, in exchange for zero service-mesh dependency.
TrainJob / ClusterTrainingRuntime
A TrainJob is "run a job using that blueprint"; a ClusterTrainingRuntime is the blueprint — same relationship as InferenceService/ClusterServingRuntime.
Caveat found: field overrides from a TrainJob only patch into recognized ML frameworks (torch/mpi/jax) — a plain custom runtime ignores them. See §10.
Kubeflow Profile
A namespace the Profile controller creates and owns for one user, with RoleBindings it manages itself.
Only one exists: kubeflow-user-example-com, owned by user@example.com — the Dashboard's namespace picker only ever shows Profile-owned namespaces.
Istio / Dex / oauth2-proxy
Istio routes and authorizes traffic at the mesh edge; Dex is the login provider; oauth2-proxy sits between them, issuing the session cookie and injecting the kubeflow-userid header downstream.
Installed only because the Dashboard has no supported standalone mode — see §08.
Aggregated ClusterRole
A ClusterRole (e.g. kubeflow-edit) with no rules of its own — it inherits rules from any other ClusterRole carrying a matching aggregation label.
Found empty: ours had zero contributing roles until KServe's own aggregated-roles.yaml was applied. See §10.

10Post-mortem

Gotchas found & fixed

Seven real failures hit during this build, each diagnosed from actual error output rather than assumption, in the order encountered.

01

Windows console can't print MLflow's emoji

Symptom
UnicodeEncodeError: 'charmap' codec can't encode character '\U0001f3c3'
Cause
MLflow prints a 🏃 emoji on run completion; Windows' default cp1252 console encoding can't render it, crashing after the run's data was already logged.
Fix
Set PYTHONIOENCODING=utf-8 before running train.py; manually patched one already-stuck run to FINISHED via the REST API.
02

MLflow 3.x saves sklearn models as .skops, not .joblib

Symptom
KServe's built-in sklearn server only reads model.joblib.
Cause
MLflow's sklearn flavor now defaults to the skops serialization format.
Fix
export_for_kserve.py — load via mlflow.sklearn.load_model() (format-agnostic), re-save with joblib.dump().
03

KServe sends arrays, the pipeline expected named columns

Symptom
"Specifying the columns using strings is only supported for dataframes."
Cause
The ColumnTransformer selected contract_type by name; KServe's V1 protocol sends a bare array with no column names.
Fix
Select the column by position ([4]) instead — works identically on a DataFrame, so the FastAPI app needed no change. Required retraining (registry v6).
04

Git Bash silently rewrote a Unix path into a Windows one

Symptom
X Exiting due to GUEST_NODE_RETRIEVE: Node C does not exist.
Cause
MSYS2's automatic path conversion turned /mnt/models-store/… into a Windows path before minikube cp ever saw it.
Fix
Prefix the command with MSYS_NO_PATHCONV=1.
05

TrainJob field overrides silently did nothing

Symptom
A TrainJob's trainer.command was ignored; the runtime's own hardcoded command ran instead.
Cause
Field-patching only applies to ML frameworks Trainer recognizes (torch/mpi/jax/…) declared via mlPolicy — a bare custom runtime has no such wiring.
Fix
Bake the desired command directly into the ClusterTrainingRuntime instead of relying on the override. Verified by inspecting the actual generated Job spec, not by re-guessing.
06

kubeflow-edit was an empty aggregated role

Symptom
User 'user@example.com' is not authorized to list serving.kserve.io/v1beta1/inferenceservices
Cause
KServe was installed via its own Helm charts, not this distro's manifests — so nothing ever carried the rbac.authorization.kubeflow.org/aggregate-to-kubeflow-edit=true label that populates the role.
Fix
Applied the official applications/kserve/kserve/upstream/aggregated-roles.yaml from the distro — not a hand-written substitute.
07

Dashboard's namespace picker didn't know "default" existed

Symptom
KServe Endpoints tile showed no data even after RBAC was fixed.
Cause
The Dashboard's namespace selector only lists Profile-owned namespaces (/api/workgroup/env-info), never arbitrary namespaces granted via a manual RoleBinding.
Fix
Deployed working copies of both InferenceServices directly into kubeflow-user-example-com, reusing the same hostPath file via a second PV/PVC.

12Reproduce it yourself

Deployment runbook

The exact sequence, in the exact order, that produced everything documented above. Each step names the gotcha it avoids inline — follow the order and none of §10's seven failures should recur.

STAGE 0

Prerequisites

before anything else
  1. Confirm the existing app still deploys clean, before adding anything on top.
    kubectl apply -f k8s/fastapi/deployment.yaml -f k8s/fastapi/service.yaml
kubectl get pods,svc
    Expect: churn-api pod 1/1 Running.
  2. Check real node resources before installing anything heavy — every later stage's "does it fit" math depends on this number.
    minikube start --cpus=4 --memory=13900mb   # Docker Desktop caps memory below 14000mb
docker inspect minikube --format 'CPU={{.HostConfig.NanoCpus}} Mem={{.HostConfig.Memory}}'
    Trust this docker inspect number, not kubectl describe node — the latter can cache a stale figure after a resize.
STAGE 1

MLflow tracking + registry

local process, no cluster changes
  1. Install MLflow and start the tracking server with a database backend from the start — a plain file store can't be upgraded to support the Registry later without redoing this step.
    pip install mlflow
python -m mlflow server --backend-store-uri sqlite:///mlflow.db \
  --default-artifact-root ./mlruns --host 127.0.0.1 --port 5000
  2. Add tracking calls to train.py (set_tracking_uri, set_experiment, start_run, log_param/log_metric, log_model(..., registered_model_name="churn-model")) — the registry name in that one kwarg is what makes every future run auto-version.
  3. Run training with UTF-8 output forced, every time, on Windows.
    PYTHONIOENCODING=utf-8 python train.py
    Skipping PYTHONIOENCODING=utf-8 reproduces gotcha §10-01 — the run logs fine but gets stuck at status RUNNING.
  4. Verify a version was actually registered before moving on.
    curl -s http://127.0.0.1:5000/api/2.0/mlflow/model-versions/search \
  -X POST -H "Content-Type: application/json" \
  -d '{"filter":"name=\"churn-model\""}'
    Expect: at least one entry under model_versions.
STAGE 2

KServe — Standard mode, no Istio yet

cluster changes begin here
  1. cert-manager first — everything else's webhooks depend on it being ready, not just applied.
    kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.17.0/cert-manager.yaml
kubectl wait --for=condition=Ready pods --all -n cert-manager --timeout=120s
  2. KServe CRDs, then the controller, explicitly in Standard mode (no Knative/Istio).
    helm install kserve-crd oci://ghcr.io/kserve/charts/kserve-crd \
  --version v0.20.0 --namespace kserve --create-namespace

helm install kserve-resources oci://ghcr.io/kserve/charts/kserve-resources \
  --version v0.20.0 --namespace kserve \
  --set kserve.controller.deploymentMode=Standard --wait
  3. The serving runtimes (sklearn, xgboost, …) are a separate chart with its own switch — easy to miss.
    helm install kserve-runtime-configs oci://ghcr.io/kserve/charts/kserve-runtime-configs \
  --version v0.20.0 --namespace kserve \
  --set kserve.servingruntime.enabled=true
    Skip this and every InferenceService fails with no runtime found to support predictor with model type — this is gotcha-adjacent to how KServe was actually first deployed here.
  4. Prove the install with the public test model before touching your own.
    kubectl apply -f k8s/kserve/inference-service-test-model.yaml   # sklearn-iris, gs:// storageUri
kubectl get inferenceservice sklearn-iris
    Expect: READY: True within ~2 minutes (image pull + model download).
STAGE 3

Your real model onto KServe

bridges the laptop filesystem into the cluster
  1. Fix the pipeline's column selection before exporting — do this in train.py, retrain, so it's baked into the artifact rather than patched after the fact.
    # ColumnTransformer(..., [4])   # position, not ["contract_type"]
PYTHONIOENCODING=utf-8 python train.py
    Skipping this reproduces §10-03 — KServe's array-based requests fail against a name-based selector.
  2. Export the registered version to the format KServe's sklearn server expects.
    python export_for_kserve.py <version-number>   # writes kserve-model/model.joblib
  3. Copy it onto the Minikube node, with path-mangling disabled if you're on Git Bash / Windows.
    minikube ssh -- "sudo mkdir -p /mnt/models-store/churn-model"
MSYS_NO_PATHCONV=1 minikube cp kserve-model/model.joblib \
  /mnt/models-store/churn-model/model.joblib
    Omitting MSYS_NO_PATHCONV=1 reproduces §10-04.
  4. Create the PV/PVC bridge, then the real InferenceService.
    kubectl apply -f k8s/kserve/churn-model-storage.yaml
kubectl apply -f k8s/kserve/churn-inference-service.yaml
    Expect: curl -X POST .../v1/models/churn-model:predict -d '{"instances":[[35,12,70.5,2,"Month-to-month"]]}' → {"predictions":[0]}.
STAGE 4

Kubeflow Trainer

optional — training orchestration only
  1. One Helm install, defaults off (no bundled LLM runtimes).
    helm install kubeflow-trainer oci://ghcr.io/kubeflow/charts/kubeflow-trainer \
  --namespace kubeflow-system --create-namespace --version 2.3.0
  2. If you want a custom runtime (not one of the bundled torch/deepspeed images), bake the command into the ClusterTrainingRuntime directly — don't rely on TrainJob.spec.trainer overrides.
    kubectl apply -f k8s/kubeflow-trainer/simple-training-runtime.yaml
kubectl apply -f k8s/kubeflow-trainer/hello-trainjob.yaml
kubectl get trainjob hello-trainjob
    See §10-05 — overrides silently no-op on custom runtimes.
STAGE 5

Kubeflow Dashboard (Istio + Dex + Profiles)

optional, the most expensive stage — check headroom first
  1. Before starting, confirm real headroom covers ~0.8 core / ~2.3 GiB minimum (Istio's control plane is the single biggest line item).
    kubectl describe node minikube | grep -A6 "Allocated resources"
  2. Render a trimmed Kustomize build — Istio, oauth2-proxy, Dex, Kubeflow namespace/roles/istio-resources, Dashboard, user-namespace only. Skip Notebooks/Katib/Pipelines/duplicate-KServe/duplicate-Trainer entirely.
    kubectl kustomize example-minimal/ > render.yaml
wc -l render.yaml   # sanity check it actually built
  3. Apply with retries — CRDs and webhooks race on a first pass.
    for i in 1 2 3 4 5; do
  kubectl apply --server-side --force-conflicts -f render.yaml && break
  sleep 15
done
  4. Grant KServe's RBAC aggregation immediately — otherwise every namespaced UI call 403s later.
    kubectl apply -f applications/kserve/kserve/upstream/aggregated-roles.yaml
    This is the fix for §10-06 — apply it as part of the install, not as a later patch.
  5. Log in and confirm the identity chain before touching any specific tile.
    kubectl port-forward svc/istio-ingressgateway -n istio-system 8090:80
# browser → http://127.0.0.1:8090 → "Sign in with Dex" → user@example.com / 12341234
    Expect: page title becomes Kubeflow Central Dashboard.
  6. Deploy any InferenceService you want the Dashboard to actually show into the Profile namespace from the start — not into default.
    kubectl apply -f k8s/kserve/churn-model-storage-profile-ns.yaml
kubectl apply -f k8s/kserve/profile-ns-inference-services.yaml -n kubeflow-user-example-com
    Deploying into default first reproduces §10-07 — the Dashboard's namespace picker never learns that namespace exists.
  7. Install the one dashboard tile actually wired up, if you want more than a shell.
    helm install kserve-ui <path-to>/kserve-ui --namespace kserve --set kubeflow.enabled=true
    Expect: /kserve-endpoints/api/namespaces/kubeflow-user-example-com/inferenceservices returns "success":true with real entries.

Stages 4 and 5 are independent of each other and of Stage 3 — skip either without breaking anything upstream. Stages 0→1→2→3 are strictly sequential.

Compiled directly from live cluster state, MLflow registry queries, and command output captured during the build session — every figure above is a fact, not an estimate.
